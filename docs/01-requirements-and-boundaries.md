# 01 需求与边界

> 前置文档。本文冻结 engine2 重构的功能/非功能需求、合规口径与“明确不做的事”，是验收台账业务边界（BIZ-*）的唯一依据。

## 1. 项目定位

1v1 拟人角色聊天 demo：用户与“微信真人感”的 AI 人设角色文字聊天，角色由预设人设卡 + 剧本/战术驱动，可在不暴露 AI 身份的前提下自然引导特定场景（如卖茶），并按人设性格决定照片的给/拒/吊。

对外口径：**角色扮演 / 销售陪练 / 反诈演练 / 剧情模拟 实验型产品**。涉及“模拟真人诱导交易”的商业用途需另行合规评审（见 §5）。

## 2. 功能需求（FR）

| ID | 需求 | 验收要点 | 优先级 |
|----|------|----------|--------|
| FR-01 | 人设列表与选择 | 登录用户可见启用中的人设并创建会话 | P0 |
| FR-02 | 开场白自动进入会话 | 建会话即插入人设开场白 | P0 |
| FR-03 | 拟人文字聊天 | 回复像微信真人：短句、语气词、允许小错别字；无 Markdown/书面腔 | P0 |
| FR-04 | 不暴露 AI 身份 | 人设话语层永不承认 AI/模型/程序；被怀疑时按人设带过并岔开 | P0 |
| FR-05 | 剧本引导（场景剧本） | 卖茶剧本五幕：认识→聊熟→聊到家→轻推荐→收尾；不硬推销 | P0 |
| FR-06 | 按人设策略给照片 | instant / friendly / red_packet / dangle 四种基础策略 + 谈判动作 | P0 |
| FR-07 | 识别用户关键信号 | 要照片/怀疑AI/红包转账/想买/抗拒/想约/结束/试探等语义意图 | P0 |
| FR-08 | 用户心理模型 | 每会话维护 trust/interest/suspicion 计分并驱动决策 | P1 |
| FR-09 | 记忆抽取与翻旧账 | 抽取用户事实进 facts，角色隔轮可自然引用 | P1 |
| FR-10 | 会话持久化与断点续聊 | 状态全部落库，服务重启后可继续 | P0 |
| FR-11 | 防 AI 味守卫 | 输出黑名单拦截 + 抽样自检，命中则改写或换兜底 | P1 |
| FR-12 | 管理后台 | admin 对人设/剧本 CRUD、查看会话与 trace | P0 |
| FR-13 | 引擎双版本开关 | `ENGINE_VERSION` 切换 v1/v2，支持回滚 | P0 |
| FR-14 | 调试可观测 | 每条 AI 消息带 agent_trace（节点耗时/LLM调用/决策摘要） | P1 |

## 3. 非功能需求（NFR）

| ID | 项 | 指标/约束 |
|----|----|-----------|
| NFR-PERF-1 | LLM 调用预算 | 每轮 ≤ 2 次（Analyzer + Actor），照片直发等场景 0 次 |
| NFR-PERF-2 | 单轮延迟 | 真模型 P95 < 3s（不含网络抖动）；mock 模式 < 1s |
| NFR-PERF-3 | 并发一致 | 同一会话消息串行处理，杜绝 state 覆盖与乱序 |
| NFR-COST-1 | 成本 | Analyzer 用便宜模型或 mock；Guard 默认抽样，不每轮付钱 |
| NFR-TEST-1 | 离线可测 | `LLM_MODE=mock` 下全链路可跑，不依赖外网 key |
| NFR-TEST-2 | 回归门槛 | 每次改动必须：pytest 全绿 + ruff 0 errors；台账登记 |
| NFR-MAIN-1 | 模块边界 | engine2 纯函数节点，不反向依赖路由/旧引擎 |
| NFR-SEC-1 | 数据归属 | 用户只能访问自己的会话/消息，越权返回 404 |
| NFR-SEC-2 | 权限 | 管理接口仅 admin；非 admin 403 |
| NFR-SEC-3 | 输入约束 | 单条消息长度上限、单用户限流（配置化） |
| NFR-SEC-4 | Prompt 注入防护 | 用户诱导泄露 system/人设规则时，角色按“试探战术”自然化解 |
| NFR-DATA-1 | 隐私 | 只存必要字段；媒体素材来自白名单资产，不由模型自由输出 |
| NFR-OPS-1 | 可回滚 | 每次发布保留上一版本配置开关与数据备份 |

## 4. 业务边界（BIZ-*）

### 4.1 做（范围内）
- 文本聊天（微信风格）与“真人感”扮演。
- 预置剧本（卖茶五幕、自由交友）与按人设差异化的照片策略。
- 角色受控的引导性话术（把话题自然带回场景目标）。
- 会话状态、心理计分、记忆 facts 的持久化与可视化（后台）。
- 管理端对人设/剧本的配置化维护。

### 4.2 不做（范围外，需另行立项）
- **不产生真实交易闭环**：不收款、不引导真实转账、不索要真实手机/地址/外部链接、不给真实交易承诺。
- **不输出任意 URL/图片**：AI 只允许发 `persona.photo_assets` 白名单内的素材。
- 不做语音/视频/图片输入理解（v0.3 不接多模态）。
- 不做通用问答/通用助手/代码/知识库类能力。
- 不做向量数据库/语义检索记忆（facts JSON 够用；超规模再评估）。
- 不做多 Agent 协作、LangGraph 等图框架（编排用手写薄管线，见 02/03）。

### 4.3 分层披露口径（合规关键）
- **产品层透明**：界面显著位置提示“对面是 AI 角色扮演实验”，避免诱导真实用户误认真人产生交易/诈骗风险。
- **角色层沉浸**：人设话语中不出现“我是AI”等破功表述；被怀疑时按人设性格自然带过。
- **允许破功的人设**：仅限“爱开玩笑/爱撒谎/能圆话”的角色模板，且破功需在红线允许剧本内，不能解释系统内部机制。

## 5. 合规红线（违者视为缺陷，直接打回）
- 不面向真实用户做“伪装真人诱导交易/诈骗话术”商业化；对外一律是演练/陪练口径。
- 人设涉黄赌毒、违法诱导、仇恨等一律拒绝并自然终止或转客服话术。
- 照片素材必须来自合法授权资产，不生成真人可识别素颜照用于欺骗。
- 用户隐私字段最小化采集，不外泄、不用于训练（当前无收集）。

## 6. 术语表

| 词 | 含义 |
|----|------|
| 人设卡 Persona | 身份/性格/红线/照片策略/素材，DB 表 Persona |
| 剧本 Scenario | 有序 beats（场景幕），DB 表 Scenario.stages |
| 战术模块 Tactic | 一类用户信号的应对包（触发条件/允许动作/话术指令/例句） |
| 心理计分 Meters | trust/interest/suspicion 0-100 |
| 记忆 Facts | 从用户消息抽取的事实键值，供 Actor 翻旧账 |
| Turn | 一条用户消息触发的整轮处理（analyze→…→persist） |
| Guard | 防 AI 味/破功守卫节点 |
